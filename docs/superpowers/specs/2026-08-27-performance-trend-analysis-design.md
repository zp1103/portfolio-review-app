# 组合绩效与趋势观察设计

日期：2026-08-27  
状态：已完成方案确认，待实施计划  
适用项目：Portfolio Review App

## 1. 背景

当前系统以每周快照为核心，已经能够记录组合总资产、持仓、交易金额、单期盈亏、累计盈亏、资产配置和穿透配置。现有页面更适合完成“本周录入与复盘”，但还不能稳定回答以下问题：

- 扣除申购、赎回等外部资金流后，组合真实表现如何；
- 组合和产品在最近 4、8、12 个录入周期的收益、回撤和动量如何；
- 产品当前处于上行、下行、震荡还是转折观察状态；
- 主动观察产品之间的相对强弱如何；
- 长期持有和稳定资产如何客观展示，而不产生不必要的交易暗示。

当前数据库已有 19 个快照、145 条持仓观察和 8 个稳定的“产品名称 + 账户类型”组合。快照间隔以 7 天为主，但存在 4 至 12 天的间隔，因此所有窗口在产品文案中统一称为“期”，不宣称是严格自然周。

## 2. 目标与非目标

### 2.1 目标

1. 增加轻量的外部净资金流确认，使组合收益能够剔除资金进出影响。
2. 为产品建立跨快照稳定身份及管理角色，避免依赖名称临时判断。
3. 提供组合和产品的 4、8、12 期收益、净值、高点、回撤、动量和连续涨跌期数。
4. 对主动观察产品提供透明、可解释、需要连续两期确认的历史状态识别。
5. 新增独立的“趋势观察”页面，不挤压现有录入复盘页面。
6. 保留退出产品的历史，并支持未来新增宽基或其他观察产品。

### 2.2 非目标

- 不建立逐笔资金流水账，不要求录入每一笔资金发生日期。
- 不接入实时行情、基金净值或外部基准指数。
- 不输出涨跌预测、目标价格、自动交易或调仓指令。
- 不使用黑箱综合评分，也不把不同周期收益压缩为一个总分。
- 第一阶段不持久化派生净值、回撤、排名或状态结果；它们由历史快照实时计算。
- 第一阶段不做产品角色的历史版本管理。角色修改只影响当前归类，不改写历史金额和收益。

## 3. 领域定义

### 3.1 产品管理角色

每个账户内的产品有一个稳定产品档案，角色取值如下：

| 角色 | 用途 | 趋势状态 | 当前约定 |
| --- | --- | --- | --- |
| `active_watch` | 主动观察 | 是 | 科创50、恒生科技、中证全指组合包及未来新宽基 |
| `long_term` | 长期持有 | 否 | 养老金账户中证500增强、养老金FOF |
| `stable` | 稳定资产 | 否 | 全球稳健、博时恒泽等 |
| `liquidity` | 流动性 | 否 | 现金 |

中证全指是一个投资组合包，不是系统基准。它作为普通 `active_watch` 产品展示，并标记为“计划退出”；在清仓后保留历史，但不再进入当前观察池排名。未来重新建立的新宽基可独立创建产品档案并加入观察池。

### 3.2 比较分组

产品档案包含 `comparison_group`：

- `broad`：宽基或宽基组合；
- `star50`：科创方向；
- `hang_seng`：恒生方向；
- `other`：其他。

第一阶段的主排名范围是所有未退出、数据完整的 `active_watch` 产品，分组作为上下文标签展示，便于理解跨市场比较。未来同组产品达到两只以上时，可以增加同组过滤或同组排名，不影响当前数据结构。

### 3.3 生命周期

产品生命周期取值：

- `active`：当前持有或正常观察；
- `planned_exit`：计划逐步退出，仍参与当前观察；
- `exited`：已退出，仅保留历史，不进入当前排名。

清仓快照保留金额为 0 的最后一条持仓及赎回金额。下一期不再复制该产品。若之后重新建仓同一产品，可继续使用原产品档案；但因为连续数据已中断，重新建仓首期不计算产品单期收益，也不会跨缺口拼接窗口。

## 4. 数据模型

### 4.1 新增 `portfolio_products`

```sql
CREATE TABLE portfolio_products (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    canonical_name TEXT NOT NULL,
    account_type TEXT NOT NULL,
    management_role TEXT NOT NULL,
    comparison_group TEXT NOT NULL DEFAULT 'other',
    lifecycle_status TEXT NOT NULL DEFAULT 'active',
    created_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
    updated_at TEXT NOT NULL DEFAULT CURRENT_TIMESTAMP,
    UNIQUE(canonical_name, account_type)
);
```

产品身份是账户相关的。同名产品如果处于不同账户，视为两个独立档案，避免养老金和普通账户的管理语义互相影响。

### 4.2 扩展 `holdings`

新增：

```sql
product_id INTEGER REFERENCES portfolio_products(id)
```

现有 `product_name` 和 `account_type` 继续保留，作为该快照的可读历史副本，并保持现有 API 和模板兼容。所有新增持仓最终都必须绑定 `product_id`。

初始化迁移按去重后的 `(product_name, account_type)` 创建产品档案，再回填全部历史持仓。迁移必须幂等；重复启动不能产生重复档案。当前数据应完整映射为 8 个产品档案和 145 条已绑定持仓。现有产品角色在迁移后由一次明确配置完成，不通过产品名称硬编码到分析算法。

### 4.3 扩展 `weekly_snapshots`

新增：

```sql
external_net_flow_amount REAL NULL,
external_flow_confirmed INTEGER NOT NULL DEFAULT 0
```

- `external_net_flow_amount`：本期外部净资金流，转入为正、转出为负；
- `external_flow_confirmed`：0 表示系统估算或尚未确认，1 表示用户确认过当前数值。

历史快照不强制批量写入估算值。当数据库字段为空时，服务在读取时动态推导，因此不会因重复初始化覆盖用户后来修正的值。

## 5. 录入流程

### 5.1 外部净资金流

从第二个快照开始，系统自动推导：

```text
估算外部净资金流 = 本期总资产 - 上期总资产 - 本期组合盈亏
```

每周录入页面增加一个轻量确认区：

1. 系统显示估算金额；
2. 用户可以直接接受，也可以修改；
3. 用户勾选或点击“确认”后保存 `external_flow_confirmed = 1`；
4. 未确认也允许保存，但趋势页明确显示“系统估算”。

首个历史快照没有上期资产，不计算资金流，也不要求确认。该设计不记录资金发生日期，不拆分多笔流入流出，符合每周复盘的录入成本目标。

### 5.2 产品身份和角色

录入已有产品时，系统沿用其稳定产品档案。首次出现的新产品需要一次性选择：

- 管理角色；
- 比较分组；
- 生命周期，默认 `active`。

后续快照自动继承。页面提供一个小型“产品设置”入口，可修改角色、分组和生命周期。修改归类不会重算或覆盖持仓历史。

### 5.3 复制快照

复制上期快照时：

- 产品身份、角色和分组继续继承；
- 交易金额、单期盈亏归零；
- 动作恢复为“持有”；
- 已退出产品不再复制；
- 外部净资金流重新估算，不能继承上期确认值。

## 6. 计算规则

所有内部计算使用未四舍五入的浮点值；只在输出边界格式化金额和百分比。

### 6.1 组合单期收益

对第二个及以后快照：

```text
组合单期收益 = 本期组合盈亏 / (上期总资产 + 0.5 × 本期外部净资金流)
```

这是适合当前每期仅有一个净资金流数值的 Modified Dietz 近似。因为没有精确发生日期，资金流按期中发生处理。页面必须称为“估算资金流调整收益”或“估算净值”，不能表达为精确份额净值。

若分母小于等于 0，则该期收益不可用，并生成数据质量提示。首个快照只作为净值基点，不生成单期收益。

### 6.2 组合净值与回撤

首个快照净值设为 1000，随后链式计算：

```text
本期净值 = 上期净值 × (1 + 本期组合单期收益)
```

如果某一期收益不可用，净值序列在该点中断；页面不跨无效期补链。

```text
本期回撤 = 本期净值 / 截至本期的历史最高净值 - 1
```

页面展示：

- 累计收益；
- 当前回撤；
- 已记录历史内的最大回撤；
- 当前阶段高点及其快照日期。

这些指标只覆盖系统中已有的历史，不宣称是产品成立以来或账户成立以来数据。

### 6.3 产品单期收益

产品必须在相邻两个组合快照中连续存在，且上期金额大于 0：

```text
产品单期收益 = 本期产品盈亏 / (上期产品金额 + 0.5 × 本期产品净交易额)
```

买入为正，赎回为负。若分母小于等于 0，该期收益不可用。首次建仓、缺期后重新出现、上期金额为 0 后重新建仓时，首期只记录金额和盈亏，不计算单期收益。

清仓期如果保留了本期金额 0 和完整赎回额，且分母有效，仍可计算清仓期收益。

### 6.4 4、8、12 期复合收益

对连续、有效的单期收益使用：

```text
窗口复合收益 = ∏(1 + 各期收益) - 1
```

窗口内任何一期缺失或无效，则该窗口显示“数据积累中”或“数据不连续”，不把缺失值当作 0，也不使用不足周期的年化或外推值。

### 6.5 动量

产品拥有至少 8 个连续有效单期收益时：

```text
近期动量差 = 最近 4 期复合收益 - 再前 4 期复合收益
```

页面同时显示两段收益和百分点差，不生成黑箱分数。正差表示近期相对增强，负差表示近期相对减弱；这只是历史变化描述。

### 6.6 连续上涨和下跌期数

- 单期收益大于 `+0.05%`：上涨；
- 单期收益小于 `-0.05%`：下跌；
- 介于两者之间：持平，并中断上涨或下跌连续计数。

页面显示最新连续上涨期数或连续下跌期数。阈值以常量集中维护，并显示规则版本。

### 6.7 相对强弱

对所有满足下列条件的产品，按 4、8、12 期分别独立排序：

- `management_role = active_watch`；
- `lifecycle_status != exited`；
- 对应窗口数据完整有效。

不合成总分。页面同时显示产品比较分组，提醒用户这是跨市场、跨风格的观察池比较，不把中证全指或任何单一产品当作基准。若某个窗口不足两只可比较产品，则显示“可比较产品不足”，不展示没有意义的名次。

## 7. 状态识别

### 7.1 适用范围

状态识别仅适用于 `active_watch` 产品，至少需要 8 个连续有效单期收益。长期持有、稳定资产和现金永远不生成战术状态。

### 7.2 候选状态规则 v1

先计算最近 4 期收益 `R4` 和最近 8 期收益 `R8`，按以下优先级判断：

1. **转折观察**：`R4` 与 `R8` 符号相反，且 `|R4 - R8| >= 1 个百分点`。页面补充“由弱转强”或“由强转弱”。
2. **上行**：`R4 > +1%` 且 `R8 > 0`。
3. **下行**：`R4 < -1%` 且 `R8 < 0`。
4. **震荡**：不满足以上条件。

12 期收益作为补充证据，不直接改变候选状态。规则顺序固定，避免同一数据同时落入多个状态。

### 7.3 连续两期确认

候选状态不直接成为确认状态。服务从历史向当前依次计算：

- 同一个候选状态连续出现两期，才更新为已确认状态；
- 候选状态只出现一期时，保留上一个已确认状态；
- 页面显示“候选状态，待确认 1/2”；
- 首次达到最低数据量但尚无任何确认状态时，显示“尚未确认”。

该过程由完整历史确定性重放，因此不需要单独持久化状态表。修正历史快照后，状态会自动按相同规则重算。

### 7.4 证据强度

证据强度是数据和规则的一致性等级，不是概率：

- **低**：刚达到 8 期、候选状态仍待确认，或存在影响窗口的质量提示；
- **中**：状态已连续两期确认，至少 8 期连续有效，且窗口内无严重质量问题；
- **高**：在“中”的基础上拥有 12 期连续有效数据，4 期与 8 期方向一致，并且动量变化或观察池相对排名至少有一项支持当前状态。

以下情况会限制强度：

- 使用窗口内存在非标准间隔时，最高为“中”；
- 有缺失或无效收益时不跨缺口，未满足最低连续期数则不输出状态；
- 外部净资金流未确认只降低组合绩效的可信度，不降低由产品交易额和盈亏计算的产品状态证据。

快照相邻日期为 5 至 9 天视为正常周频；其他间隔仍算一个录入期，但标记为非标准间隔。

### 7.5 声明

页面固定展示：

> 本页面仅基于已录入的历史数据进行状态识别，不构成涨跌预测、交易建议或调仓指令。

## 8. 软件架构

采用“独立分析模块 + 按需计算”的方案，避免继续扩大现有 `PortfolioService`，也避免过早引入分析结果缓存表。

### 8.1 模块边界

```text
app/
  analytics/
    returns.py       # 单期收益、窗口复合收益、净值链
    metrics.py       # 高点、回撤、连续涨跌、动量、排名
    classifier.py    # 候选状态、两期确认、证据强度
  performance_service.py  # 读取并组织历史数据，输出页面视图模型
  product_service.py      # 产品档案创建、映射和维护
```

- `returns.py`、`metrics.py` 和 `classifier.py` 是无数据库依赖的纯计算模块；
- `PerformanceService` 负责从数据库加载时间升序数据、构建连续序列、调用计算模块，并形成组合与产品视图模型；
- `ProductService` 负责产品身份、角色、分组、生命周期和迁移映射；
- 现有 `PortfolioService` 继续负责快照录入、配置、归因和数据质量，不承载趋势算法。

### 8.2 数据流

```text
weekly_snapshots + holdings + portfolio_products
                    │
                    ▼
            PerformanceService
                    │
        ┌───────────┼───────────┐
        ▼           ▼           ▼
     returns      metrics    classifier
        └───────────┼───────────┘
                    ▼
          趋势观察页视图模型
                    ▼
            /analysis + Jinja
```

所有查询按日期升序计算，输出时根据页面需要组织。对于当前规模，实时计算成本可忽略。若以后数据量明显增长，再在不改变纯函数接口的前提下增加缓存。

### 8.3 规则版本

状态阈值、间隔阈值和连续涨跌阈值集中定义为一个规则配置，并暴露规则版本，例如 `trend-v1`。趋势页显示版本，便于以后调整规则时解释历史结果变化。

## 9. 页面设计

### 9.1 导航和路由

顶部导航增加：

- `录入复盘`：现有 `/`；
- `趋势观察`：新增 `/analysis`。

不把趋势模块堆叠到现有首页，保证每周录入流程的操作密度不增加。

### 9.2 组合表现区

展示：

- 估算资金流调整净值曲线；
- 累计收益；
- 当前回撤和历史最大回撤；
- 阶段高点及日期；
- 最新外部净资金流金额和“已确认/系统估算”状态；
- 数据覆盖范围和质量提示。

若历史中存在未确认资金流，净值曲线仍可展示，但标题和提示明确包含“估算”。

### 9.3 主动观察区

每个当前 `active_watch` 产品显示一张摘要卡：

- 4、8、12 期收益；
- 当前回撤；
- 连续上涨或下跌期数；
- 最近 4 期与前 4 期动量差；
- 已确认状态；
- 候选状态和 `1/2` 待确认提示；
- 证据强度；
- 比较分组和生命周期标签。

计划退出产品仍正常计算和展示，不因计划本身改变状态结果。

### 9.4 观察池比较区

以表格分别展示 4、8、12 期收益及各自名次。每个周期独立判断数据是否完整。退出产品不参与当前排名，但可在历史产品区域查看过去指标。

### 9.5 长期与稳定资产区

长期持有和稳定资产只展示：

- 4、8、12 期收益；
- 当前回撤和阶段高点；
- 数据覆盖情况。

不展示上行、下行、转折、待确认或调仓文案。现金不进入趋势页产品列表。

### 9.6 可用性文案

必须区分：

- `数据积累中`：尚未达到窗口长度；
- `数据不连续`：中间缺少相邻快照或产品记录；
- `计算不可用`：分母无效等数学条件不成立；
- `可比较产品不足`：排名样本少于两只；
- `系统估算`：外部净资金流尚未确认。

不能用 0% 替代任何不可用指标。

## 10. 异常与边界处理

1. **没有快照**：趋势页展示空状态和录入入口，不报错。
2. **只有一个快照**：净值基点为 1000，其余收益指标显示数据积累中。
3. **快照日期重复**：沿用现有唯一约束并返回可理解的录入错误。
4. **历史产品未映射**：数据质量区列出记录，趋势计算跳过该记录；新写入不允许未映射产品。
5. **金额或分母异常**：对应指标不可用，不抛出整页异常。
6. **快照间隔异常**：保留一期计算，但打质量标记，并限制证据强度。
7. **产品缺期**：中断连续窗口；重新出现后从新连续段开始积累。
8. **资金流未确认**：组合指标继续使用系统估算值并显著标记；产品指标不受影响。
9. **产品退出**：保留所有历史，移出当前观察排名，不物理删除档案。
10. **角色修改**：只改变页面当前归类和未来录入默认值，不改写历史持仓事实。

## 11. 测试设计

### 11.1 纯计算单元测试

- 最近 4 期与前 4 期动量差；
- 各周期独立排名和不足两只的情况。

### 11.2 分类器表驱动测试

- 上行、下行、震荡、由弱转强和由强转弱；

- 只有一期候选时保持原确认状态；
- 连续两期相同候选后确认；

### 11.3 数据迁移与服务测试

### 11.4 页面与回归测试

- 现有 API、录入、编辑、复制、配置、归因、穿透和数据质量测试全部继续通过。

## 12. 验收标准

1. 每次录入可以看到并确认一个外部净资金流，无需维护逐笔流水。
2. 组合页能够显示有明确“估算”含义的资金流调整净值、收益、高点和回撤。
3. 数据完整时，每个适用产品能够显示 4、8、12 期收益、动量、回撤和连续涨跌期数。
4. 只有主动观察产品显示状态，并严格执行连续两期确认。
5. 长期持有和稳定资产只显示客观指标，不出现战术提示。
6. 中证全指计划退出期间正常展示，退出后保留历史但不参与当前排名。
7. 新建宽基只需配置一次产品角色和分组即可进入后续观察。
8. 数据不足、数据中断、无效分母和未确认资金流都有可区分的界面提示。
9. 所有规则均能通过纯函数测试复现，页面显示 `trend-v1` 规则版本。
10. 现有功能无回归，数据库迁移可重复执行。

## 13. 后续扩展边界

以下能力不在本次实现计划中，但当前边界为其保留了扩展空间：

- 接入外部基准后计算超额收益；
- 同组产品数量增加后的组内排名；
- 精确到日期的资金流和标准 Modified Dietz；
- 规则版本历史与状态快照缓存；
- 更长周期、滚动波动率或风险调整收益。

任何后续扩展都不应改变本期的核心语义：状态识别描述历史，不预测未来，也不自动给出交易指令。
